Trig Against the Calculator

Qwen3.8-27B was asked for sin, cos and tan across a full cycle in degrees, to exactly five decimal places, and every answer scored against Python's math in double precision. Mathematics is verifiable rewards.

Is it accurate like a scientific calculator?
No. One answer in three is wrong with no scratchpad, and the way it fails is not how arithmetic fails.

Ask for sin(361°) and it returns 0.62932 — which is sin(39°), exactly. A wrong calculation lands on an arbitrary number near the right one; this lands on a crisp table entry for the wrong angle. Ask for an angle no table covers, sin(37.87°), and it gets three decimals right and the fourth wrong. Retrieval supplies the fifth decimal; its own arithmetic is worth about three.

Accuracy tracks the trig table

Thinking off, split by how often an angle appears in a printed table. No account in which the model computes makes sin(35°) easier than sin(34°) — the arithmetic is identical. An account in which it remembers predicts exactly this.

Two different failures

Of the answers that are wrong, how many are still an exact five-decimal value of that function at some other angle? A broken lookup returns a crisp entry for the wrong key. A broken computation does not.

Where the answer lives inside the model

A linear probe reading the first decimal digit of the answer off the residual stream at the last prompt token — before a single character is generated. Baseline is 20.6%, the majority-class rate, not 10%: the digit 9 is over-represented because |sin| and |cos| pile up near 1.0.

What this does not show: that it knew better than it said. The true and said digits agree on 80.3% of rows, so the probe cannot separate those two, and the wrong-only subset is too small to train on. These activations also came from batches of 48, and the last-token residual is not invariant to batch padding.
